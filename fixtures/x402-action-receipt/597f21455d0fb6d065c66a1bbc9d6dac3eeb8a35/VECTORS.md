# Conformance vectors — coverage matrix

Committed inputs, generated by `action_receipt.py --regenerate` and verified by the
default run (36 vectors: 7 positive, 29 negative). Two-sided: both PASS and REJECT
arms, the run asserts it observed both verdicts, and asserts every reject reason in
`ALL_REASONS` (13 codes) was exercised by a negative. Fails (exit 2) if either
meta-assertion doesn't hold.

**Coverage granularity.** The meta-assertion is over the 13 reason *codes*. Several
codes aggregate multiple verification branches (e.g. `invalid_actionreceipt_settlement_mismatch`
has five emit sites; `invalid_actionreceipt_signature` funnels several signature
causes; `invalid_payload` covers all structural/type checks). To keep those from
being blind, the vector set carries a dedicated negative for each *sub-branch* below,
not just one per code. Keys derive from fixed seeds (reproducible); ECDSA signatures
differ across regenerations, so regeneration is opt-in and the default run only
verifies. A missing `keys.json` is a hard error in verify mode (no silent self-heal).

## Notes on the harder cases

- `neg_payto_wrong_resource` proves the scoped-anchor fix: `KID_PAYTO` is registered
  only for `(PAY_TO, RESOURCE)`; a receipt it signs for a *different* `resourceUrl`
  is `invalid_actionreceipt_signer` — closing the "a payee key can attest any service"
  gap.
- `neg_uncorroborated_transaction` is a batch receipt (`settlementRef` matches) carrying
  a bogus non-empty `transaction`; §5.10 rejects it so an unverified hash can't ride
  into `actionRef`.
- `neg_wrong_curve` is signed by a secp256k1 key under an `ES256` header; the curve/alg
  binding rejects it at §5.7.
- `neg_noncanonical_payload` is validly signed over non-canonical bytes; rejected purely
  by §5.5. `neg_forged_actionref` is correctly signed over its forged body; caught only
  by §5.6.
- `neg_settlement_failed` is a well-formed receipt verified against a `success:false`
  settlement — the failure is on the settlement side (§5.9).

## keys.json

Public keys by `kid`, plus `__service__:<resourceUrl>` and
`__payTo__:<payTo>|<resourceUrl>` entries listing authorized kids (the two scoped,
fail-closed §5.8 anchors). Deterministic across regenerations.

## MANIFEST.json — portable, language-neutral reuse

`vectors/MANIFEST.json` makes this suite runnable by a verifier in **any** language,
not just the Python reference. It carries, for every vector, the expected verdict and
(on REJECT) the reason code, plus the named settlement context to evaluate it against
(`settlements` block). A TypeScript / Go / Python implementation loads `keys.json`, each
vector file, and the named settlement, and MUST reproduce the manifest's verdict/reason.
It is projected from the same `SUITE` / `SETTLEMENTS` the Python runner uses, so the two
cannot drift.
