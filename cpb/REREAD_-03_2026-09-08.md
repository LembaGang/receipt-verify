### C-2's summary, checked against the bytes rather than assumed

> "§8's payload data format moves to a COSE protected header parameter; the
> algorithm is unchanged."

**Both halves hold, with one qualification.**

The first half is confirmed twice over. `-03` §8 opens: *"This section defines a
typed digest reference as an abstract information model: four members, their
meaning, and their requiredness. It does not fix a payload serialization. CPB
defines an optional protected-header serialization in Section 8.3."* §8.3 then:
*"A CPB-bound Signed Statement MAY carry its typed digest references as a COSE
protected header parameter, cpb-refs, registered in Section 14.2. The parameter
MUST NOT occur in the unprotected header."* — with a normative CDDL
(`cpb-refs = [1*64 typed-digest-reference]`, integer keys 1–4, closed).

The second half holds **for §4.1**, which is byte-identical, and that is the
section this repository implements. It does **not** hold for §4 as a whole: §4.2
is rewritten at length (see F1–F3 below), §4.4 is reworded throughout, §14.1's
registry is restructured from Table 3 to Table 4 with new required fields, and §3
gains a `RAW-DIGEST` definition that `CANONICAL-DIGEST` is now expressed in terms
of. So: *the jcs construction* is unchanged; *§4* is not.

## Findings

### F1 (behavioural). `-03` requires **Failed** where we return `unverified` for an unestablished vintage

`cpb/algorithm.ts` returns, when no commit date is supplied:

```ts
reason: "algorithm_withdrawn_jcs_n_vintage_unknown", disposition: "unverified"
```

asserted by `test/cpb/construction.test.ts:320` ("does not take the vintage
allowance when no commit date is supplied", `expect(r.disposition).toBe("unverified")`).

`-02` gave no rule for that case; the choice was recorded as `AMBIGUITY_LOG` A19.
`-03` §4.2 states one:

> "A verifier encountering jcs-n with evidence of a time at or after the cutoff,
> **or without sufficient evidence of a pre-cutoff vintage**, MUST fail closed and
> MUST NOT report the payload class or typed digest reference as verified; a typed
> reference has the **Failed** outcome."

Under `-03`, an unestablished vintage is `Failed`, not the weaker "nothing was
established". The direction of the error is the safe one — we already refuse — but
the state we report is the wrong one, and a consumer branching on `disposition`
would treat a `-03`-Failed record as merely unproven.

**Not fixed here.** The fix is one branch and one test line; it belongs in a
session scoped to change code.

### F2 (input contract). `recordCommittedOn` is exactly the evidence `-03` forbids

`AdmissionContext.recordCommittedOn` is documented as "the date the record was
committed, as an ISO-8601 date or date-time … the draft does not say where a
verifier reads it from — see AMBIGUITY_LOG A19". `-03` §4.2 now says where it may
**not** come from:

> "Pre-cutoff vintage is established only by profile-defined, cryptographically
> verifiable evidence that binds the exact record, or its digest under the declared
> context, to a time before that cutoff. A payload timestamp, **source-control
> commit date**, file-system time, transport arrival time, or other unauthenticated
> date MUST NOT be used as vintage evidence."

A bare ISO string supplied by a caller is an unauthenticated date by construction.
`-03` therefore answers A19 **against** the reading taken from `-02`: the parameter
type is wrong, not just under-specified. A `-03` implementation takes verifiable
evidence, or takes nothing and reports Failed.

### F3 (unresolved ambiguity now resolved). The cutoff has a timezone in `-03`

`AMBIGUITY_LOG` A20 records: *"§4.2 writes the date bare, three times, and never as
a timestamp… Recorded rather than resolved — the text supports no particular
answer."* The implementation does lexicographic comparison with no timezone
normalisation.

`-03` §4.2: **"The vintage cutoff is the start of 2026-08-18 UTC."** A20 is answered.
The lexicographic comparison at `algorithm.ts` is unchanged and still does not
normalise an offset, so a record dated `2026-08-18T00:30:00+03:00` — before the
cutoff in UTC — still sorts on or after `"2026-08-18"` and is reported `failed`.
Fail-closed, and now demonstrably not what the text says.

### F4 (vocabulary / agent contract). `-03` defines a closed four-state outcome vocabulary; ours has three, and one is not in it

`cpb/types.ts` declares `Disposition = "verified" | "failed" | "unverified"`, with a
comment citing §4.2's "unverified rather than as failed" sentence — which `-03`
removes. `-03` §3 defines, as terms, six states: **Signature-Valid**,
**Issuer-Authenticated**, and the four typed-reference processing states
**Malformed**, **Unresolved**, **Failed**, **Verified**. §2 lists this as one of the
revision's headline changes.

`unverified` has no counterpart in `-03`. Both places we return it map to
**Unresolved**, and `-03` says so in as many words:

- jcs-n, pre-cutoff, construction not implemented → §4.2: *"A verifier that lacks an
  implementation of the otherwise eligible historical construction reports the typed
  reference as **Unresolved**."*
- `as-transmitted`, registered but not implemented → §3 *Unresolved*: *"…or it lacks
  the implementation needed to execute an otherwise valid digest context."*

That also answers `AMBIGUITY_LOG` **A21** ("no general rule for an algorithm a
verifier simply has not implemented"), which `-02` did not carry and which the
implementation resolved by analogy. `-03` supplies the general rule, and the
analogy turns out to have been right in substance and wrong in name.

This is the finding that matters most for agent consumption: the reason tokens are
a closed vocabulary a consumer branches on, and a token that no longer exists in the
governing document is a contract that reads as current and is not.

### F5 (transcription). `-03`'s registry is Table 4 with new required fields; we transcribe Table 3

`CANONICALIZATION_ALGORITHM_REGISTRY` transcribes `-02` §14.1 Table 3, whose columns
are Name / Description / Reference, and models `status` as `"registered" | "withdrawn"`.

`-03` §14.1 replaces it with **Table 4** and a different required field set: Name,
**Status**, Preimage construction, **Hash function and typed-reference token**,
**COSE hash algorithm**, Output representation, **Test vectors**, Reference. The
status vocabulary is **Active / Reserved / Withdrawn** — `"registered"` is not one of
them. The initial contents now also declare, for entries our table leaves blank:

| entry | `-03` Table 4 | `algorithm.ts` today |
|---|---|---|
| `jcs` | Active, SHA-256 / SHA-256, COSE `-16`, 64-char lowerhex, vectors §14.1.1 | `status: "registered"`, `digest: "SHA-256"`, `encoding: "lowercase-hex-64"` |
| `jcs-n` | Withdrawn, **SHA-256 / SHA-256, COSE `-16`, 64-char lowerhex** | `status: "withdrawn"`, no `digest`, no `encoding` |
| `cde-n` | Withdrawn, N/A throughout | `status: "withdrawn"`, no `digest`, no `encoding` |
| `as-transmitted` | Active, SHA-256 / SHA-256, COSE `-16`, 64-char lowerhex | `status: "registered"`, both declared |

No behaviour turns on the missing cells today — `jcs-n` never returns `ok`, so its
digest and encoding are never read. It is a divergence in what the file *claims* the
registry says.

### F6 (stale comment). `-03` restates the jcs-n construction that `-02` did not

`cpb/algorithm.ts`'s header comment says:

> "We decline to implement the withdrawn construction — deliberately. Its definition
> lives in -00 §3.1, which -02 does not restate, and reading it is out of scope for
> an implementation written from -02."

True of `-02`. `-03` §4.2 **does** restate it — five numbered steps, duplicate-name
rejection before data-model conversion, an integer-form number grammar with an
explicit `[-(2^53-1), 2^53-1]` range, top-level exclusion, bottom-up
null/empty-array/empty-object removal, then JCS + SHA-256 + lowercase hex, closing
with `CANONICAL-DIGEST(jcs-n, P, E) = lowercase_hex(SHA-256(JCS(normalize(P minus E))))`.
The decision to decline can stand; the reason given for it no longer describes the
governing text. `-03` adds its own guard on that: *"Evaluating the construction and
obtaining matching bytes does not by itself establish an eligible vintage or produce
a Verified typed-reference outcome."*

`-02` named none. `-03` §14.1.1 *Test Vector Locations* names three public
locations, all under `https://github.com/action-state-group/scitt-payload-binding/tree/main/vectors/`
(`jcs`, `jcs-n`, `as-transmitted`).

The repository resolves (`HTTP 200`) and was cloned to a scratch directory outside
this repository, at `c5e0435f3e00221f87b39c6f5d14b2b5211e9db9`
(`Merge pull request #82 from tyche-dev/codex/cpb03-final-editorial-cleanup`,
2026-09-05). **Nothing from it is pinned here**: these vectors are not a corpus this
repository holds, and every result below is against bytes in a scratch clone.

91 files under `vectors/`, of which the two that name `jcs` — the only algorithm this

| vector | `must_fail` | result |
|---|---|---|
| `vectors/jcs/pass/01-retain-null-and-empty-members.json` | false | **MATCH** — our pre-image is byte-equal to their `pre_image_bytes_hex`, and our digest `7b3ef8ebf31ee38952860dd3f30c2e0d101dcdbcd9972e3ed8108ef9cff0d7cb` equals their `digest` exactly |
| `vectors/jcs/fail/01-duplicate-member-name.json` | true | **MATCH** — refused, `reason=payload_duplicate_member_name`, section `§4.1 → RFC 8785 §3.1 → RFC 7493 §2.3`; their `failure_reason` is `jcs_duplicate_member_name` |

The pass vector is deliberately the one that discriminates `jcs` from the withdrawn
`jcs-n`: its input carries a `null`, an empty object and an empty array, all of which

is the input which would have turned this check red had `canonical-digest.ts` carried
the normalization pass, and it did not.

The fail vector's rejection is the delegated rule `cpb/types.ts` records as the one
that "was missed once" — `jcs`'s registry Reference is RFC 8785 §3, whose §3.1
requires I-JSON, which forbids duplicate member names. `-03` publishing a vector for
exactly that case corroborates the delegation independently.

**What was not run, and why.** The other 89 files cover algorithms and mechanisms this
implementation does not execute: `jcs-n/kats` (38) and `jcs-n/derived-id` /
`assembled-preimage` (5) are the withdrawn construction we decline; `as-transmitted`
(2) is registered but not implemented (§4.4); `typed-refs` (11), `cpb-check` (13),
`registry` (4), `subject-binding-diff` (6), `domain-transforms` (2),
`profile-independence` (2), `multimodal` (1) and `representation-contrast` (1) are
`-03` mechanisms with no `-02` counterpart and therefore no implementation here at
all. Running them would report our absence, not our behaviour.

## Verdict per file in scope

**`cpb/canonical-digest.ts` — still matches `-03`.** Its governing section, §4.1, is
byte-identical between the revisions; §12.1 and §12.3, the two other sections it
cites, are reworded and byte-identical respectively with no rule change; §3's
CANONICAL-DIGEST is restructured through the new RAW-DIGEST but resolves to the same
value (`ENCODE_A(H_A(A(v)))` = `ENCODE_A(RAW-DIGEST(A, v))`), and the file already
returns both the raw 32 octets and the 64-character hex. Confirmed, not merely
argued, by `-03`'s own two `jcs` vectors above. **No finding.**

**`cpb/algorithm.ts` — does not match `-03`.** Six findings: F1 (a wrong outcome
state), F2 (an input contract `-03` forbids), F3 (an ambiguity `-03` closes and the
code still does not implement), F4 (a disposition token that no longer exists), F5
(a registry transcription one revision out of date), F6 (a stale justification).
Only F1 changes what a caller receives today.

**`test/cpb/construction.test.ts`** encodes F1 and F4 as assertions —
`construction.test.ts:309` ("reports a pre-withdrawal jcs-n record unverified, not
failed"), `:320` ("does not take the vintage allowance when no commit date is
supplied", `expect(r.disposition).toBe("unverified")`) and `:329` (`as-transmitted`)
— so it is green against `-02` and would have to move with any fix. That is the
correct state for a suite that tests a `-02` implementation. `unverified` is also
asserted outside `algorithm.ts`'s scope (`construction.test.ts:242`, a §5.1
representation case), so F4's vocabulary change reaches further than these two
files.

## Flagged, outside this re-read's scope

Named because a changed section governs them, not analysed here — the handoff scoped
this re-read to `algorithm.ts` and `canonical-digest.ts`:

- **`cpb/leaf.ts` / §7.1.** The most substantive rule change in the revision. `-02`
  made the raw 32-byte form mandatory for a VDS keyed on the derived identifier
  (`leaf_input = bytes.fromhex(D)` "correct", the UTF-8 form "WRONG … MUST NOT be
  used"). `-03` makes it a **declaration**: *"The VDS or an applicable profile MUST
  state which one is its leaf input… If the declaration instead selects the textual
  CANONICAL-DIGEST, the latter 64 ASCII bytes are the declared input. A verifier
  constructing a leaf MUST apply the declared selection and MUST NOT infer it from
  the apparent shape of the value."* `leafInput` returns the raw 32 octets on every
  path (decoding `hex` when the identifier carries the textual representation) and
  rejects any length other than 32; its `VdsKeying` interface carries one member,
  `keysOnDerivedIdentifier: boolean`, and no way to state **which** representation
  the VDS declared. Under `-03` that is correct for one of the two permitted
  declarations and unable to express the other. `-03` also loosens the length
  assumption the file records against A15: *"Algorithms registered later may have
  different output sizes."*
- **`cpb/derived-identifier.ts` / §5, §5.1.** `-03` deletes `-02`'s selective-disclosure
  paragraph ("the derived identifier MUST be computed over the SD-encoded form") and
  replaces it with a general profile-transform rule closing *"This document defines no
  such transform."* The reason token `sd_encoded_form_required` in `cpb/types.ts` is
  named for a `-02` sentence that `-03` does not carry. §5.1 also adds a digest-context
  representation rule whose violation is the `Failed` state.
- **`cpb/discover-section5.ts`, `cpb/mutants.ts`, `cpb/run-vectors.ts`,
  `cpb/AMBIGUITY_LOG.md`, `cpb/PROVENANCE_T1.md`, `cpb/T3_RESULTS.md`,
  `cpb/T3B_RESULTS.md`** and their `.external` siblings all cite `-02` section and
  line numbers. None was re-read.

## What this re-read does not establish

- **It is a reading, not a run.** F1–F6 are differences between what `-03` says and
  what the code does. Only the two `jcs` vectors were executed; nothing else here was
  verified by running it.
- **`AMBIGUITY_LOG.md` is not updated.** A19, A20 and A21 are answered by `-03` and
  still stand in that file as open against `-02`, which is accurate of `-02`.
- **The `-03` vectors are not pinned.** They live in a scratch clone at
  `c5e0435`; nothing in `fixtures/` or `refs/` holds them, and a later session that
  wants to cite the two results above has to pin them first.
- **Sections nobody implements were not read closely.** §6.1/§6.2, §8.2–§8.5, §14.2
  and Appendix D are new mechanisms with no counterpart in this implementation; they
  are named above and no verdict is offered on them.
