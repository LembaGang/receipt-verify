## 0. What this document is, and is not

**A check with no known-bad input is a constant, not a check.** Every check this methodology applies, and every conformance check in a suite it grades, ships with at least one input the check must reject, and the suite fails if the check ever passes that input. A check that has never gone red proves nothing when it reads green; three of the defects found in September 2026 (a chain check that accepted any non-empty link, a chain explorer that reported both correct chains it was given as broken, a fixture set and reader built to one revision that agreed by construction) were checks that could not change state, and each read exactly like a passing check from outside. Where a check in a graded suite has no known-bad input, the entry records that as a finding against the suite, not as a pass. The companion test, from a reviewing author (§8): "declared but unimplemented" and "implemented and passing" must not be able to render the same.

This is the **methodology**. It is versioned and dated separately from any report that applies it, so a result published under v0.2 can always be reconciled to the rules in force when it was produced. Changing a rule requires a new version of this document and a stated effective date. It does not silently change past results.

**This document does not rank formats.** It defines seven properties, each with a determinate answer arrived at by a stated procedure that anyone can repeat. There is no composite score and no letter grade. A reader who wants a ranking must construct one and own the weighting.

A single grade invites two failures. It can be optimised against without improving the property underneath, and it converts a set of checkable facts into one contestable opinion. What is recorded here can be argued with only by being checked.

**Verdicts are issued separately for the specification text and for each implementation, and are never merged.** Where the text is correct and an implementation does not recompute it, the specification's row records that, the implementation's row records that, and the entry names what went unchecked. One merged verdict hides which half earned it. (This rule resolves former open question 3; see Acknowledgments.)

**What is measured is what a third party can determine from published artifacts**: the specification text, the published vectors if any, the published verification key material, and the distributed implementation artifact. Nothing depends on access to a graded party's runtime, source repository, or cooperation.

**Entries assess an implementation in a role, not a format in the abstract.** An *emitter* produces records; a *verifier* evaluates them. Some axes apply to one role only, and every entry states which role it assessed. Where a format has implementations in both roles, each takes its own entry. Where a role has no published implementation, the axes specific to it are recorded as **not determinable** rather than as absent, and the entry says so.

## 1. The organising split, and the finding that forced it

Two different claims get collapsed into the word "pass," and separating them is the whole design.

**Specification implementability** — could a correct implementation be written from the published text alone? **Reference-implementation fidelity** — does the shipped code do what the specification says? A format can satisfy either without the other, and that combination is the most useful thing a reader can learn.

The evidence for the first is the existence of an independent implementation (§2.4). There is no other way to establish it: a specification can only be shown implementable by someone implementing it without help.

The second needs two measurements rather than one, and here is why.

During preparation of this methodology the editor measured the following on his own published package: a released artifact was missing an entire feature described in its own documentation, and the **full conformance corpus passed against it**. Every vector green. The corpus could not observe the gap, because a corpus only exercises what the corpus exercises, and nothing in the repository bound the distributed artifact to the source tree it was cut from.

So "reproduces the published vectors" (§2.2) and "exposes what its documentation describes" (§2.3) are separate axes. Any methodology that reports only the first will report green on an artifact that is missing a feature, and no reader will be able to tell.

§2.3, §2.6, and §2.7 are the same mechanism at three levels. Each is a hand-maintained declaration of what is and is not covered, checked against what is actually there: §2.3 declares the surface the documentation claims and tests the artifact against it; §2.6 declares the checks the verifier does not perform and carries that with the verdict; §2.7 declares which normative requirement each published vector exercises and leaves the unexercised requirements visible. The gap described above was caught by the first. A corpus passing against an artifact missing a feature is exactly what an unmapped requirement looks like from the outside.

**Declarations carry their timing.** A declaration committed before the run it governs constrains the evaluation; one arrived at afterwards is a response to it. Both can be honest, and the record distinguishes them: every declaration relied on in an entry states whether it predates the run, and a declaration amended after the fact is amended by dated addendum stating which way the selection effect cuts. This is cheaper to check than the declared fact itself — a reader who cannot verify the fact can still verify that the declaration predates the run that used it. (See Acknowledgments.)

## 2. The seven axes

### 2.1 Canonicalisation posture
*Applies to: the specification. Role-independent.*

How does the specification determine the bytes that get signed? One of:

- **Fixed** — names a canonicalisation algorithm normatively (e.g. RFC 8785).
- **Own** — defines its own canonicalisation rules in full.
- **Delegated** — explicitly declines to define canonicalisation, assigning it to a subordinate document.
- **Declared** — canonicalisation is carried per artifact, declared in the artifact's own metadata.
- **Unstated** — none of the above.

*Recorded as a fact, not a defect.* Delegated and Declared are legitimate designs. The axis exists because a specification that composes with another cannot establish byte agreement with it unless both postures are known, and because a family that delegates cannot have that property asserted on its behalf.

**Procedure:** read the specification text. Record the section that determines it, or record that none does.

### 2.2 Vector agreement
*Applies to: emitters and verifiers.*

Does the **distributed artifact** reproduce the published test vectors?

**Procedure:** obtain the published package rather than the source repository. Execute it against each published vector. Record per vector, and record **no published vectors** where none exist.

### 2.3 Artifact–specification agreement
*Applies to: emitters and verifiers.*

Does the distributed artifact expose the surface its own documentation describes?

**Procedure:** import the distributed artifact and probe for each documented entry point. Record what is absent. This axis exists because §2.2 cannot detect a missing feature that no vector exercises.

### 2.4 Independent recomputability
*Applies to: the format. Determined across all known implementations, in any role.*

Has a party that did not author the specification produced an implementation from the published text alone, and does it recompute the same bytes?

- **Independent** — a different party built from the published text, no shared code path, no coordination on implementation, and the outputs agree byte for byte.
- **Prepared** — two code paths, one party. Includes a generator and a verifier shipped in the same bundle, and a second implementation written by the specification's own author.
- **Single** — one implementation.

A worked example of the Independent value, for calibration: `giskard09/argentum-core` PR #28 (merged 2026-07-02) added a conformance set for `verification.v0.3+composed` built by a party other than that specification's author, and PR #33 (merged 2026-07-16) re-signed one vector after a strict RFC 8785 verifier ordered a member's keys differently from the non-strict serialisation the original signature had been made over. The second is the more instructive half: independent recomputation is worth recording precisely because it surfaces divergences that a single party's two code paths cannot.

*The distinction is not a criticism.* A prepared pair establishes internal consistency and nothing about the specification: a misreading is reproduced identically on both sides and the suite still passes. **The editor's own corpus is Prepared and is recorded as such.**

This axis carries the specification-implementability claim from §1. Independent is the only value that establishes it, because a specification can only be shown implementable by someone implementing it unaided.

### 2.5 Verification key model
*Applies to: the format. Determined from the specification and the issuer's published key material.*

How does a relying party obtain the verification key? One of: **published key set** (retrievable without credentials), **shared secret**, **out of band**, or **unstated**.

### 2.6 Coverage declaration
*Applies to: **verifiers only**. An emitter evaluates nothing. Where a format has no published verifier, this axis is not determinable.*

Does the verifier declare what it does **not** check, and does that declaration travel with the result? One of:

- **Declared** — non-coverage is machine-readable in the output, present on every result including passing ones.
- **Documented** — stated in prose somewhere, but not carried by the verdict.
- **Absent** — neither.

The axis is named after the mechanism rather than the failure it prevents, because the mechanism is the thing an implementer can build. A verdict silent about what was not checked cannot distinguish a check that ran and passed from one that does not exist in the tool. Two verifiers that both pass every vector in a corpus, one of which states its blind spots and one of which does not, are not the same artifact, and only the first is safe to cite.

This axis is the one that makes the other six honest, which is why it is recorded on every entry and why the "travels with the result" half is not optional. A coverage statement in a README describes the tool. A coverage statement in the output describes the verdict a reader is about to rely on.

### 2.7 Vector requirement mapping
*Applies to: the format's published vector corpus. Not determinable where no corpus is published.*

Does a published mapping state, for each vector, which normative requirement of the specification it exercises — and are the requirements exercised by no vector left visible as unmapped? One of:

- **Declared** — a published, machine-readable mapping ties each vector to the requirement it exercises, and lists the normative requirements no vector exercises.
- **Documented** — prose claims about corpus coverage exist, but no per-vector mapping.
- **Absent** — neither.

The axis records the declaration, not a proportion. "What fraction of requirements do the vectors exercise" requires adjudicating the specification, which is a different job from measuring artifacts; the mapping is determinable from published artifacts by a third party, it cannot be gamed by adding vectors — an unmapped requirement stays visible no matter how many vectors exist — and the fraction falls out of the mapping for any reader who wants to compute it. The declaration is the part an implementer can actually build.

This is the third instance of the §1 mechanism, and the finding in §1 is the argument for it: a corpus passing against an artifact missing a feature is exactly what an unmapped requirement looks like from the outside.

**Procedure:** obtain the published corpus and mapping. Verify that mapped requirement identifiers exist in the specification text and that mapped vectors exist in the corpus. Spot-check that sampled vectors exercise the requirement claimed. Record the published unmapped-requirement list, or record that no mapping is published.

## 3. Non-coverage of this methodology

Every entry carries its own non-coverage statement recording, at minimum: which axes were not determinable and why; which artifact versions and specification revisions were examined, by digest; any axis whose determination rests on the editor's reading rather than an executed check; and, for every declaration relied on (§2.3 surface, §2.6 coverage, §2.7 mapping), whether that declaration predates the run that used it — with dated addenda where it does not.

**Known limits of the method:**

- It measures published artifacts. A format whose implementation is private cannot be assessed on §2.2–2.4, and that is recorded as not-determinable rather than as failure.
- §2.1 is determined by reading. Two careful readers may disagree; §5 exists for that.
- Every entry is a snapshot, true of the artifact versions named in it and of nothing else.

Disclosure alone is insufficient. Two structural measures apply:

**The editor's own entries and any format he has materially shaped are re-run by another party.** A co-signatory or other independent implementer recomputes those rows and the result is published with the re-runner named. An entry not independently re-run is labelled **unverified**, in the same way any other unconfirmed result would be.

**Every determination is reproducible from published code and pinned inputs**, so a graded party can dispute a row with a counter-measurement rather than an assertion.

## 5. Governance

**Review window.** Before publication, each graded party receives the entries concerning them and a fixed period to recompute and object. Objections and their resolution are published alongside the entry.

**Right of reply.** A graded party may submit a response of any length. It is published with the entry, unedited.

**Corrections.** Published entries are immutable. An error is corrected by a new dated entry superseding the previous one; the superseded entry remains visible with a forward pointer. No silent editing. A superseded result and an assessment error are distinct events and are labelled as such: the first records that the artifact changed, the second that the editor was wrong about the artifact as it stood.

**Re-testing.** Entries update only on a new dated run against newly pinned artifacts. A fix is not reflected until the re-run happens, and the previous entry is not deleted when it does.

**Versioning and citation.** Each report is published under a dated immutable identifier alongside the digest of the inputs it was computed from, so a result cited elsewhere stays checkable after the artifacts move on.

## 6. Candidate axes, not adopted

Considered and deliberately not adopted as of this version. Each is arguably measurable; none is clearly worth the weight yet. Co-signatory views wanted.

**Signature preimage determinacy.** Can two independent readers of the specification alone derive byte-identical signing input for the same logical record? Determined by walking every step from record to preimage — member ordering, number formatting, string escaping, whether the signature member is excluded, absent, or null. *Argument against: it may be a restatement of §2.1 plus §2.4, and it is expensive to determine.*

**Offline verifiability.** Can a relying party verify with no call to the issuer at verification time, given only the record, the published key material, and the specification? *Argument against: for every format examined so far, this follows from §2.5 and adds no information.*

## 7. Open questions for co-signatories

1. **Is §2.4 sufficient evidence for specification implementability?** An independent implementation demonstrates it. Its absence demonstrates nothing. Should there be a weaker positive value for a specification whose canonicalisation and preimage are fully determined but which nobody has yet implemented independently?

2. **Should §2.4 distinguish independence further** — an implementer who read only the specification, versus one who also read the reference implementation? The distinction is real and may be unverifiable in practice.

3. **Vocabulary for the §1 split.** "Specification implementability" is proposed as the neutral term, with the IETF two-independent-implementations tradition (RFC 2026 §4.1.2) and W3C's independent-implementation requirement as pedigree. Alternatives welcome, provided a reader outside this group can look the term up.
