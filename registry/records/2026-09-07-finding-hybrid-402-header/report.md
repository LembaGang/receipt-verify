**Kind:** finding-in-own-work, assigned by the contributor.

**What it showed:** "One defect in the contributor's own worker, surfaced by the first run of a stock 2.x x402 client against it. The `Payment-Required` header declared `x402Version: 1` while carrying the version-2 field name `amount` and omitting version 1's mandatory `resource` and `description`, so it matched neither the version-1 nor the version-2 schema in `@x402/core` 2.20.0. The response body beside it was a schema-valid version-1 object. A 2.x client reads the header first and never consults the body, so it parsed the header, then failed at payload creation with `Failed to create payment payload: No client registered for x402 version: 1`, before any signature and before any network matching. No stock 2.x client could pay the worker while that header was served. The class is the same as Row 21's: a product that said one thing in two places, and a verifier (here, a client) that trusted the wrong one. Repair: the worker now serves a version-2 `Payment-Required` header beside the version-1 body from one canonical object; the header is validated in the test suite against the client's own schema declarations, vendored from `@x402/core` 2.20.0 (`test/vendor/x402-schemas.mjs`, source file sha256 `19c189f7…`), and the exact broken `accepts[0]` of 7 September is asserted to fail both schemas, so the defect cannot return silently."

**Disclosure and repair timeline:** "captured 2026-09-07 09:27:34 UTC by this contributor's own run; taken into the record the same morning; fix committed 10:27:47 UTC; the live worker still served the hybrid at 11:35:27 UTC (pre-deploy check); deployed 12:41 UTC; confirmed live 12:42:32 UTC; settled against at 13:01:57 UTC, when the same stock 2.20.0 client paid the served 402 (Base mainnet transaction `0x46db8fc8cfd79017375d76c5ad80256950f8437ff009ecbe90b6cd5ce97e9263`, block 50,998,385, 1,000 atomic units of USDC to the advertised pay-to address, read from the chain by this contributor rather than from the server's settlement header). Three hours and fourteen minutes from capture to live fix; three hours and thirty-four minutes to a settlement against it. A second settlement by the same client class followed at 16:37:35 UTC (`0x94bfba79…`, block 51,004,854). A third party's 2.25.0 client parsed the served version-2 requirement and built a payment signature in simulation the same evening, reported by that party and not verified here."

**What it does not establish:** "That any version-1 client ever paid the version-1 body: the body was schema-valid throughout, but no 1.x client was run against it, before or after the fix. That any client other than `@x402/fetch` 2.20.0 pays the worker: one client, one language, two settlements. That the worker's other published surfaces were free of the same class: two of them (`/openapi.json` and `/.well-known/x402.json`) carried unrendered template placeholders on the same day, found by this contributor's own patch inspection rather than by a client, and fixed in the following commit (`261c48a`); that is a second finding in own work and is recorded separately. The defect is stated from the captured bytes and the repository's commit record; the capture carries no worker version identifier (the response headers name a CF-RAY only), and none is reconstructed here."

**Prior art:** "none claimed for the defect. The repair mechanism, validating a served header against the consuming client's own vendored schema declarations and pinning the exact broken bytes as a failing case, is ordinary contract testing; no precedence is claimed."

**Non-comparable pairs:** As Row 21: "No comparison pair was identified using both an independent implementation and independently derived vectors." The capture was this contributor's own client against this contributor's own worker.
